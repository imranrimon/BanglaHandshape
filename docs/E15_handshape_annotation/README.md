# E15 — Expert handshape-annotation package (draft for verification)

**Reviewer point (§28).** *"Rename `Sign N` → the actual Bengali character, and get a
native-signer / SL-linguist handshape-similarity annotation; then test whether the
signer-independent (SI) errors fall along handshape-similarity lines
(correlate similarity with the SI confusability / per-class Δ\_SI)."*

This directory is the **pre-filled annotation package** so the human step is
*verification*, not from-scratch labelling. Everything here is a **DRAFT / HYPOTHESIS**;
the expert's edits are the ground truth and the actual contribution.

The claim E15 supports: **the SI accuracy drop is phonologically sensible** — classes
that collapse under a signer shift are the *articulatorily similar* handshapes, not a
random subset. That turns "SI is hard" into "SI errors respect handshape structure,"
which is a much stronger, mechanism-level statement.

## What's in here

| File | Who fills it | Purpose |
|---|---|---|
| `sign_to_bengali_DRAFT.csv` | expert **confirms/corrects** | folder `Sign N` → Bengali grapheme + Roman. The correspondence is the *first* thing to verify. |
| `handshape_feature_coding_sheet.csv` | expert **fills** (37 rows) | one articulatory feature vector per handshape. Pairwise similarity is **derived** from this — no O(N²) rating needed. |
| `pairwise_validation_sheet.csv` | expert **fills** (~30 rows, round 2) | holistic 0–4 similarity on a *stratified sample* of pairs, to validate that the feature-derived similarity tracks human judgment (Spearman ρ). **Generated by the analysis script after the feature sheet is filled** — a header-only template is shipped here for reference. |

Then run:

```bash
python -m tools.handshape_similarity_analysis \
    --source bdsl47_letters \
    --feature-csv docs/E15_handshape_annotation/handshape_feature_coding_sheet.csv \
    --confusion-npz work_dir/bhc_lora/confusion_bdsl47_letters_seed0.npz \
    --per-class-gap results/T3_per_class_gap_bdsl47_letters.csv \
    --out results/E15
```

It (1) builds the feature-derived similarity matrix, (2) correlates it with the SI
**confusability** matrix (from the existing SF1 confusion export) and the per-class
**Δ\_SI** gap, (3) writes the round-2 `pairwise_validation_sheet.csv`, and (4) emits
`results/E15/E15_correlation.md` + a scatter PNG for the paper.

## Why folder → character must be *verified*, not assumed

Every source stores classes as integer-stringified folders (`Sign 0`, `Sign 1`, …).
The dataset papers' label dictionaries are not redistributed with the images, so we
**cannot assume `Sign 0` is `অ`**. The `proposed_bengali` column below is the natural
"folders are in alphabet order" hypothesis — it is exactly what the expert confirms
or re-orders. Getting this right is a genuine, citable contribution (the field
currently trains on unlabelled indices).

### Bangla reference (for the expert to pick from)

**Digits (০–৯):** ০=0, ১=1, ২=2, ৩=3, ৪=4, ৫=5, ৬=6, ৭=7, ৮=8, ৯=9.

**Vowels — স্বরবর্ণ (11):** অ a · আ aa · ই i · ঈ ii · উ u · ঊ uu · ঋ ri · এ e · ঐ oi · ও o · ঔ ou

**Consonants — ব্যঞ্জনবর্ণ (39):** ক ka · খ kha · গ ga · ঘ gha · ঙ nga · চ ca · ছ cha · জ ja · ঝ jha · ঞ nya · ট tta · ঠ ttha · ড dda · ঢ ddha · ণ nna · ত ta · থ tha · দ da · ধ dha · ন na · প pa · ফ pha · ব ba · ভ bha · ম ma · য ya · র ra · ল la · শ sha · ষ ssa · স sa · হ ha · ড় rra · ঢ় rha · য় yya · ৎ khanda-ta · ং anusvara · ঃ visarga · ঁ chandrabindu

BdSL sign alphabets use a **reduced ~37-sign inventory** (homorganic/rare letters are
merged or dropped, following the Ishara-Lipi / BdSL alphabet convention). The
`proposed_bengali` column seeds the 37 folders with `11 vowels + ক…য (26 consonants)`
as a starting hypothesis — **re-order / substitute freely**.

## Handshape feature-coding scheme (the low-burden core)

Instead of rating all 666 letter pairs, code **one row per handshape** with these
articulatory features (HamNoSys-lite / SL-phonology standard). Pairwise similarity is
then computed as weighted feature agreement — 37 codings replace 666 ratings.

| Column | Allowed values | Notes |
|---|---|---|
| `selected_fingers` | subset of `I M R P` (space-joined), or `none` | extended/active fingers (thumb coded separately). e.g. `I`, `I M`, `I M R P` |
| `thumb` | `tucked` · `side` · `across` · `extended` · `opposed` | thumb configuration |
| `flexion` | `straight` · `bent` · `curved` · `hooked` · `fist` | flexion of the selected fingers |
| `spread` | `together` · `spread` · `na` | finger spacing (`na` if <2 selected) |
| `contact` | `none` · `thumb-index` · `thumb-middle` · `cross` · `other` | finger/thumb contact |
| `aperture` | `open` · `flat-O` · `tight-O` · `closed` · `na` | opening between thumb and fingers |
| `expert_confidence` | `high` · `med` · `low` | your certainty about the folder→character id |
| `notes` | free text | anything (allographs, movement-only distinctions, …) |

The analysis weights: `selected_fingers` and `aperture` dominate (they define the
gross shape), `thumb`/`flexion`/`spread`/`contact` are secondary. Weights are in
`tools/handshape_similarity_analysis.py` (`FEATURE_WEIGHTS`) and are reported in the
paper so the derivation is transparent.

### Similarity rubric (for the round-2 validation sheet, 0–4)

- **0** — clearly distinct (different selected fingers *and* aperture)
- **1** — mostly distinct (one shared coarse feature)
- **2** — moderately similar (same selected fingers *or* same aperture)
- **3** — highly similar (differ in one subtle feature — thumb/contact)
- **4** — near-identical static shape (told apart mainly by orientation or movement)

## How this lands in the paper

- **T3 / §Analysis:** report Spearman ρ between feature-derived handshape similarity and
  (a) SI confusability and (b) per-class Δ\_SI, with the validation-round ρ showing the
  feature coding tracks holistic human similarity. A significant positive ρ is the
  E15 headline: *the signer-shift gap concentrates on articulatorily-similar handshapes.*
- **Naming:** the verified `sign_to_bengali` map lets every figure/table use real
  Bengali graphemes instead of `Sign N`, and is released as a dataset artifact.
